# Tailoring V2 — Evidence-Driven, Editable CV Plan

Date: 2026-11-22  
Status: Proposed — not approved for implementation yet

## 1. Problem

Current tailoring is a **job-specific overlay** on the reusable Resume Studio CV:

- Editable inputs are limited to `tailoredSummary`, `tailoredHeadline`, `tailoredSkills`, `selectedProjectIds`, `jobDescription`, and the tracer-links toggle.
- The PDF is generated by cloning the base resume in memory and applying those fields.
- There is no persisted, fully editable tailored CV document per job.
- AI generation overwrites fields instead of preserving approved manual edits.
- The tailoring prompt receives mostly the raw job description plus a whitelist of profile facts; structured job facts such as title, employer, location, degree requirements, disciplines, `jobBrief`, and per-job notes are not passed in.
- Review affordances are weak: no before/current diff, no “why this changed”, no claim evidence, no ATS checklist, no version history.
- Readiness is inconsistent across the tailoring banner, `canFinalizeTailoring()`, and the application-kit panel.
- The default prompt encourages “Keyword Stuffing”, which can improve ATS matching but can also produce unsupported or hard-to-defend claims.

The result: tailoring can create a useful first draft, but it is not yet a trusted, editable, evidence-backed CV workflow.

## 2. Goals

1. Make tailoring **evidence-based**: every generated claim should map to a real profile/project/experience fact.
2. Make tailoring **review-first**: the user sees what changed, why, and from which evidence before accepting.
3. Make the tailored CV **fully editable per job**, not just a few strings plus a PDF.
4. Improve job compatibility through **grounded keyword alignment**, not invented experience.
5. Preserve manual edits during regeneration.
6. Add a separate **tailored-fit** signal without contaminating the existing candidate-independent suitability score.
7. Keep all current product invariants: explicit AI actions, no AI on open, review-first send, tenant scoping, and sanitized prompts.

## 3. Non-goals

- Do not build a second competing CV editor that duplicates Resume Studio.
- Do not let AI silently rewrite the whole CV.
- Do not invent years, tools, metrics, seniority, or responsibilities.
- Do not change the source suitability score based on tailored output.
- Do not add AI calls on page open, job open, or email preview.
- Do not auto-send applications or auto-mark jobs as applied.

## 4. Target architecture

```text
Resume Studio (canonical CV layout + baseline facts)
        │
        ├── Global Career Evidence Bank (structured, reusable verified facts/rules)
        │
        ▼
Tailoring Plan (JD requirements → matched evidence → proposed wording)
        │  user accepts / edits / rejects
        ▼
Tailored CV Snapshot (full per-job resume JSON + change log)
        │
        ▼
Validated PDF (ATS checks + unsupported-claim checks)
        │
        ▼
Tailored-fit score (separate from source suitability score)
```

### 4.2 Global Career Evidence Bank

This is the structured version of the “global text” idea. It should be reusable, tenant-scoped, and whitelisted into LLM prompts.

Example shape:

```json
{
  "targetRoles": ["Senior Java Backend Engineer", "Backend Engineer"],
  "coreSkills": [
    {
      "name": "Java",
      "years": 8,
      "level": "expert",
      "evidence": ["project:payments-platform", "job:senior-java-engineer"],
      "aliases": ["JVM", "Core Java"]
    },
    {
      "name": "Spring Boot",
      "years": 7,
      "evidence": ["project:payments-platform"],
      "aliases": ["SpringBoot", "Spring"]
    }
  ],
  "achievements": [
    {
      "text": "Reduced API p95 latency from 800ms to 180ms",
      "evidence": "project:payments-platform",
      "metric": "77% reduction"
    }
  ],
  "alwaysInclude": ["microservices", "REST APIs", "PostgreSQL"],
  "neverClaim": ["Kubernetes administrator", "Team lead"],
  "preferredTerms": ["Spring Boot", "OAuth2", "CI/CD"],
  "avoidTerms": ["full-stack ninja", "rockstar"]
}
```

Rules:

- Store facts, not prose.
- Every skill or achievement should have at least one evidence reference.
- AI may reorder, emphasize, and rephrase supported facts. It may not create new facts.
- Reuse this bank for tailoring, scoring, cover letters, and Ghostwriter where appropriate.
- Keep sensitive fields out of prompts unless explicitly required and sanitized.

### 4.3 Tailoring Plan

Generated only on explicit **Generate / Regenerate** action.

Plan item shape:

```json
{
  "jdRequirement": "Spring Boot experience",
  "evidenceRefs": ["project:payments-platform", "job:senior-java-engineer"],
  "proposedWording": "Built production Spring Boot microservices...",
  "status": "ready",
  "supportLevel": "strong",
  "userDecision": "accepted"
}
```

The UI should let the user **Accept / Edit / Reject** each item.

### 4.4 Tailored CV Snapshot

Persist a full per-job resume JSON document, versioned.

```json
{
  "jobId": "...",
  "version": 3,
  "baseResumeRevision": 12,
  "resumeJson": {},
  "changes": [
    {
      "path": "basics.summary",
      "before": "...",
      "after": "...",
      "reason": "Matched Java/Spring Boot requirement",
      "evidence": ["project:payments-platform"]
    }
  ],
  "ats": {
    "matchedKeywords": ["Java", "Spring Boot", "OAuth2"],
    "missingKeywords": ["Kubernetes"]
  },
  "generatedAt": "..."
}
```

PDF generation should render from the approved snapshot, not from loose fields applied to the base resume at render time.

## 6. Implementation phases

### Phase 1 — Quick wins and trust improvements

**Goal:** improve tailoring quality without changing the data model.

Tasks:

1. Pass structured job context into tailoring.
   - Include `title`, `employer`, `location`, `jobBrief`, `suitabilityReason`, degree/discipline fields, and per-job notes.
   - Files:
     - `orchestrator/src/server/pipeline/orchestrator.ts`
     - `orchestrator/src/server/services/summary.ts`
     - `shared/src/prompt-template-definitions.ts`
     - `orchestrator/src/server/services/summary.test.ts`

2. Fix the missing-skills regeneration gap.
   - Include `tailoredSkills` in the skip condition.
   - Files:
     - `orchestrator/src/server/pipeline/orchestrator.ts`
     - `orchestrator/src/server/tailoring-flow.test.ts`

3. Preserve manual edits on regeneration.
   - Pass prior approved values into the prompt as “approved context”.
   - Add explicit “Keep mine / Use AI / Undo to original” per section.
   - Files:
     - `orchestrator/src/server/services/summary.ts`
     - `orchestrator/src/client/components/tailoring/TailoringWorkspace.tsx`
     - `orchestrator/src/client/components/tailoring/TailoringSections.tsx`

4. Add a review layer.
   - Show original baseline, current value, AI suggestion, and change reason.
   - Files:
     - `orchestrator/src/client/components/tailoring/TailoringWorkspace.tsx`
     - `orchestrator/src/client/components/tailoring/TailoringSections.tsx`
     - `orchestrator/src/client/components/tailoring-utils.ts`
     - Related tests in `orchestrator/src/client/components/tailoring/`.

5. Unify readiness checks.
   - Single checklist for JD, summary, headline, skills, projects, PDF, and tracer links.
   - Reuse in tailoring banner, application kit, and job page sidebar.
   - Files:
     - `orchestrator/src/client/components/tailoring/rules.ts`
     - `orchestrator/src/client/components/tailoring/TailoringWorkspace.tsx`
     - `orchestrator/src/client/pages/orchestrator/JobDetailPanel.tsx`
     - `orchestrator/src/client/pages/job-page/JobPageRightSidebar.tsx`
     - `orchestrator/src/client/lib/pdf-freshness.ts`

6. Surface effective global writing rules inside tailoring.
   - Show language, tone, constraints, do-not-use terms, summary word cap, and keyword cap.
   - Link to Settings.
   - Files:
     - `orchestrator/src/client/components/tailoring/TailoringWorkspace.tsx`
     - `orchestrator/src/client/pages/settings/components/ChatSettingsSection.tsx`
     - `orchestrator/src/client/pages/SettingsPage.tsx`

**Acceptance criteria:**

- Opening tailoring or a job still makes no AI call.
- AI runs only on explicit Generate/Regenerate.
- Manual edits survive regeneration unless the user explicitly chooses to replace them.
- All readiness surfaces report the same state.
- Tests cover structured job context, missing-skills generation, manual-edit preservation, and review rendering.

### Phase 2 — Global Evidence Bank and grounded planning

**Goal:** replace unsupported keyword stuffing with evidence-backed matching.

Tasks:

1. Define and migrate the Global Career Evidence Bank data contract.
   - Shared types, settings schema, repository support, tenant scoping.
   - Files:
     - `shared/src/types/settings.ts`
     - `orchestrator/src/server/db/schema.ts`
     - `orchestrator/src/server/db/migrate.ts`
     - `orchestrator/src/server/api/routes/settings/*`
     - `orchestrator/src/client/pages/SettingsPage.tsx`

2. Build a settings UI for the Evidence Bank.
   - Tabs or sections: Target Roles, Skills Catalog, Achievements, Rules, Never Claim.
   - Show evidence links to Resume Studio projects/jobs where possible.

3. Use the Evidence Bank in prompts.
   - Tailoring, cover letter, and scoring/Ghostwriter where appropriate.
   - Replace “Keyword Stuffing” language with “evidence-bound keyword alignment”.
   - Files:
     - `orchestrator/src/server/services/summary.ts`
     - `orchestrator/src/server/services/scorer.ts`
     - `orchestrator/src/server/services/post-application/recruiter-email.ts`
     - `shared/src/prompt-template-definitions.ts`

4. Generate a Tailoring Plan on explicit action.
   - JD requirements → evidence → proposed wording → user decision.
   - Store decisions as part of the per-job tailoring state or new plan table.

5. Add ATS coverage and unsupported-claim checks.
   - Matched/missing keywords.
   - Exact job title present in headline.
   - Word/keyword caps.
   - Unsupported skills flagged before PDF generation.

**Acceptance criteria:**

- Every AI-proposed claim shows evidence or is blocked.
- `neverClaim` terms never appear in generated CV/letter text.
- ATS panel matches current generated content.
- Prompt templates remain configurable.
- Sensitive evidence fields are whitelisted/truncated before LLM calls.

### Phase 3 — Editable tailored CV artifact

**Goal:** make the tailored CV a real per-job document.

Tasks:

1. Add a `tailored_resumes` table or equivalent per-job JSON artifact.
   - Fields: job ID, tenant/workspace scope, version, base revision, resume JSON, change log, ATS result, model/version, generated timestamp.
   - Files:
     - `orchestrator/src/server/db/schema.ts`
     - `orchestrator/src/server/db/migrate.ts`
     - `orchestrator/src/server/repositories/jobs.ts`
     - `shared/src/types/jobs.ts`

2. Persist the prepared resume JSON before rendering.
   - `prepareTailoredResumeForPdf()` output becomes a durable artifact.
   - Files:
     - `orchestrator/src/server/services/pdf.ts`
     - `orchestrator/src/server/services/rxresume/index.ts`
     - `orchestrator/src/server/services/rxresume/tailoring.ts`

3. Add a full per-job editor for high-priority jobs.
   - Keep the existing quick overlay editor for fast jobs.
   - Add “Open full tailored CV” for deep editing.
   - Show diff against baseline.
   - Files:
     - `orchestrator/src/client/components/tailoring/TailoringWorkspace.tsx`
     - New components under `orchestrator/src/client/components/tailoring/`.

4. Render PDF from the approved snapshot.
   - Update fingerprint/freshness logic to include snapshot version.
   - Files:
     - `orchestrator/src/server/services/pdf-fingerprint.ts`
     - `orchestrator/src/server/pipeline/orchestrator.ts`

5. Add version history and restore.
   - Every generation/editing session creates a new version.
   - Users can compare and restore prior versions.

**Acceptance criteria:**

- A user can edit any CV field for one job without changing the global baseline.
- PDF generation uses exactly the approved tailored snapshot.
- Diff and version history show what changed and why.
- Tenant/workspace scoping is enforced on reads, writes, files, and background jobs.

### Phase 4 — Tailored-fit score and continuous improvement

**Goal:** measure whether tailoring actually improved compatibility.

Tasks:

1. Add a derived `tailoredFitScore` and notes.
   - Keep source `suitabilityScore` unchanged.
   - Compare tailored snapshot/Résumé JSON against JD requirements.
   - Files:
     - `orchestrator/src/server/services/scorer.ts`
     - `orchestrator/src/server/db/schema.ts`
     - `shared/src/types/jobs.ts`
     - `orchestrator/src/client/components/tailoring/TailoringWorkspace.tsx`
     - `orchestrator/src/client/pages/orchestrator/JobDetailPanel.tsx`

2. Show tailored-fit next to source fit with clear labels.
   - Do not replace the existing score.
   - Keep **Rescore** as an obvious sidebar button.

3. Add feedback loop.
   - Track which accepted suggestions led to interviews/responses.
   - Improve weighting over time without changing factual evidence.

**Acceptance criteria:**

- Source scoring remains candidate-independent.
- Tailored-fit is explicitly labelled as derived and job-specific.
- Rescore remains manual and obvious.

## 7. Cross-cutting invariants

- All `/api/*` responses follow `{ ok, data/error, meta.requestId }`.
- Honor/generate `x-request-id`; include it in logs and async flows.
- Treat every server-side change as multi-tenant by default.
- Scope DB reads/writes, caches, files, background jobs, and prompts by tenant/workspace.
- Use `infra/logger.ts`; no direct `console.log/warn/error` in core paths.
- Redact sensitive keys and truncate large payloads before logging/returning details.
- No raw upstream bodies or large `JSON.stringify(...)` blobs in errors/logs.
- No AI on open; only explicit Generate/Regenerate/Rescore.
- Review-first apply flow remains unchanged.
- Webhook/LLM payloads remain minimal and documented.
- User-visible behavior changes require docs updates.
- Push only to `fork/main`; leave `origin/main` untouched.
- Kiri rebuild stays one step via `npm run docker:rebuild:kiri`.

## 9. Open questions

1. Should the Evidence Bank be edited in Settings, Resume Studio, or both?
2. Should every job get a full tailored CV snapshot, or only `ready`/high-score jobs?
3. How many versions should be retained per job?
4. Should unsupported claims block PDF generation or only warn?
5. Should tailored-fit run automatically after PDF generation, or only on explicit request?
6. How should evidence references survive Resume Studio item deletion/renaming?

## 10. Recommended next step

Start with **Phase 1**. It delivers the biggest immediate quality and trust improvement without introducing a new data model, and it preserves all current product invariants.

After Phase 1 is landed and validated, choose between:

- **Phase 2** if the main pain is “AI writes things I cannot verify”, or
- **Phase 3** if the main pain is “I need to edit the whole CV per job”.
